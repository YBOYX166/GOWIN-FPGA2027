# 4K 侧工程（Tang Nano 4K / GW1NSR-LV4C）—— 机械臂模块开发

## 0. 这个工程是干什么的

138K 板子暂时用不了。这个工程用来**先把机械臂控制模块写完、写对**，等新的
BX72（GW5AT-138）板子到了，再整体移植进 `fpga_project/`。

**核心原则：这里只放可移植的纯 RTL。** 一切和器件绑定的东西都隔离在 4 个文件里，
移植时这 4 个不搬。

```text
4k/
├── fs/                        ← ★ 编译好的固件，直接拿去烧
│   ├── servo_serial.fs        ←   当前版本（串口微调）
│   └── README.md              ←   烧录位置说明（SRAM vs Flash，必看）
├── tools/
│   ├── build_fs.sh            ← 一条命令重新编译出 .fs
│   ├── servo_gui.py           ← 上位机 GUI：4 个滑块拖动控制
│   └── servo_send.py          ← 上位机命令行：监听 / 交互 / 批量发
└── fpga_project/
    ├── fpga_project.gprj      器件: GW1NSR-LV4CQN48PC6/I5 (gw1nsr4c-000)
    ├── src/
    │   ├── top.v              ← 顶层（POR + LED + 舵机 + 串口，双模式切换）
    │   ├── servo_pwm.v        ← [可移植] 角度(0-180°) -> 20ms/50Hz PWM，3 级流水
    │   ├── servo_sweep.v      ← [可移植] 三角波扫描（模式 1 用）
    │   ├── servo_cmd.v        ← [可移植] 串口协议解析 + 回复，3 级流水
    │   ├── uart_rx.v          ← [可移植] 8N1 接收器
    │   ├── uart_tx.v          ← [可移植] 8N1 发送器（从 138K 主工程原样复制）
    │   ├── clk_gen.v          ← [不可移植] 27MHz 时钟（直通 / PLLVR 两方案）
    │   ├── bx4k.cst           ← [不可移植] 引脚约束
    │   ├── bx4k.sdc           ← [不可移植] 时序约束
    │   ├── pnr_dual_purpose.tcl ← [不可移植] MODE 脚放开
    │   └── arm_*.v            ← [可移植] ★ 以后加逆解/PID 等都放这里
    └── impl/                  编译产物
```

## 1. 器件与时钟（最重要的事实）

| 项 | 4K 侧（本工程） | 138K 侧（`fpga_project/`） |
|---|---|---|
| 器件 | GW1NSR-LV4CQN48PC6/I5 | GW5AT-LV138PG484AC1/I0 |
| 封装 | QFN48P / 39 个用户 IO | PG484A / 291 个用户 IO |
| LUT4 | 4,608 | 138,240 |
| BSRAM | 180 Kbit / 10 块 | 6,120 Kbit / 340 块 |
| 18×18 乘法器 | **16** | **298（DSP）** |
| PLL | 2 | 12 |
| **系统时钟** | **27 MHz（引脚 45）** | **50 MHz（引脚 Y18）** |

> 时钟是 27MHz 不是 50MHz。烧进去后 LED 心跳应该是 **1 秒一次**；
> 如果看到约 0.54 秒一次，说明某处误用了 `50_000_000`。

**时钟方案：27MHz 直通（不用 PLL）**。原因：所有模块都以 `CLK_FREQ` 参数化，
传 27MHz 时的绝对时间行为和 138K 上 50MHz 完全等价，没必要凑频率。

`src/clk_gen.v` 里同时提供了 **PLLVR 版本（`pll_27`）**，27MHz 进 / 27MHz 出，
端口形状完全相同，改 `top.v` 里一处例化的模块名即可切换。什么时候该切、
以及这颗芯片 PLL 的踩坑记录（原语叫 `PLLVR` 不叫 `rPLL`、VCO 公式不同、
VCO 范围 600~1200MHz），全部写在 `src/clk_gen.v` 的注释里。

## 2. 当前功能：串口微调 4 路舵机

### 2.1 ⚠️ 供电警告 —— 先看这条再看接线

**4 个舵机的电源绝对不能从 Tang Nano 4K 的 3.3V / 5V 排针取。**
一个 MG996R 堵转就能吃 2A 以上，4 个一起上直接把板子拉垮，轻则 FPGA 复位，
重则烧掉 LDO。

```text
  独立 5V 电源（≥3A，舵机专用）  ──┬── 舵机 0 红线
                                  ├── 舵机 1 红线
                                  ├── 舵机 2 红线
                                  └── 舵机 3 红线

  舵机棕线（GND） ──┬── 独立电源 GND
                    └── Tang Nano 4K 的 GND   ← 「共地」必须有，不能省
  Tang Nano 4K servo[0..3] ── 舵机橙线（信号）

  舵机电源和 FPGA 电源是两套，只有 GND 连在一起。
```

信号线是高阻输入，FPGA 只送 50Hz PWM，不涉及驱动电流。
（好消息：±45° 都是从中位往两边各摆，属于轻载，不会持续堵转。）

### 2.2 引脚与接线

板子上有丝印标着引脚号，对着找即可。

| 信号 | FPGA 引脚 | 方向 | 电平 | 接到 |
|---|---|---|---|---|
| `servo[0]` | **43** | out | 3.3V | 舵机 0 信号线（橙/黄） |
| `servo[1]` | **42** | out | 3.3V | 舵机 1 信号线 |
| `servo[2]` | **41** | out | 3.3V | 舵机 2 信号线 |
| `servo[3]` | **40** | out | 3.3V | 舵机 3 信号线 |
| `uart_tx` | **44** | out | 3.3V | 串口 TX（FPGA → 电脑） |
| `uart_rx` | **46** | in | 3.3V | 串口 RX（电脑 → FPGA） |
| `Clk` | 45 | in | — | 板载 27MHz 晶振，**不用接** |
| `Led` | 10 | out | — | 板载红灯，**不用接** |

四个舵机脚在物理上是相邻的一组，接线不容易错。

**供电（再说一遍，接错会烧板）：**

```text
  独立 5V ≥3A ──┬── 舵机0 红
                ├── 舵机1 红
                ├── 舵机2 红
                └── 舵机3 红
  舵机棕线 ──┬── 独立电源 GND
             └── Tang Nano 4K 的 GND     ← 共地必须有
  FPGA 43/42/41/40 ── 舵机橙线
```

#### ⚠️ 电平：3.3V，而且必须显式写进约束

这些脚全在 **Bank 0 / Bank 1，板子是 3.3V 供电**，所以 `bx4k.cst` 里
每一行都写了 `IO_TYPE=LVCMOS33 ... BANK_VCCIO=3.3`。

**不能省略** —— 省略的话 Gowin 会按 `LVCMOS18` / 1.8V 处理（我实测踩到了，
引脚报告里整列都是 LVCMOS18）。依据是你本机的官方例程
`~/Desktop/乱七八糟/TangNano-4K-example-main/`：

| 例程文件 | 证明了什么 |
|---|---|
| `led_test/project/src/led_test.cst` | `clk=45`、`led=10`、`sys_rst_n=15` |
| `camera_hdmi/src/dk_video.cst` | **40/41/42/43/44/45/46 全是 LVCMOS33** |
| `key_blink/src/key_blink.cst` | `led(10)` 是 3.3V；`key(14,15)` 才是 1.8V |

所以这块板确实有三种电压：**Bank 0/1 = 3.3V**（我们用的），
**Bank 3（14/15 脚）= 1.8V**，**Bank 2（33 脚）= 2.5V**（官方例程用 LVCMOS25）。

#### ⚠️ 串口到底连哪，资料互相矛盾，需上板确认

- 第三方资料（demandperipherals 的 4K 支持页）说 **44=TX、46=RX**，即板载 USB 串口
- 但官方 `camera_hdmi` 例程把 **44 当 SCL、46 当 SDA**，是摄像头 I2C

两者不可能同时成立。**退路很稳妥**：拿一个外接 USB-TTL 模块（CH340/CP2102 之类），
接 **44(TX) / 46(RX) / GND** 三根线，一定能用，完全不依赖板载桥接。

### 2.3 串口协议

**每次发 4 个 ASCII 数字：`<舵机号><角度百位><十位><个位>`**

| 位 | 含义 |
|---|---|
| 第 1 位 | 舵机编号，只能是 `1` / `2` / `3` / `4` |
| 第 2-4 位 | 角度值 |

- **收满 4 位立即执行**，所以带不带回车都行。
- 非数字字符（回车、换行、空格）会清空计数。这样 `2\n090` 这种被拆断的帧
  不会误触发，发错了也不会乱动。
- 只有被点到的那一路会动，其余保持不动 —— 这就是"微调"。

**回复**（每收一条命令回一行）：

```text
S2=090 A045        <- 2 号舵机，收到原值 090，实际转到 45 度
ERR                <- 编号不是 1-4，或角度超范围
```

**上电默认**：4 路都停在 90 度（中位），等你发指令。

### 2.4 FPGA 会主动发三种信息（★ 出问题时靠这个定位）

| 什么时候发 | 内容 | 说明 |
|---|---|---|
| 复位后约 0.5 秒，**只发一次** | `=== Tang Nano 4K Servo Ready ===`<br>`Send 4 digits, e.g. 2090` | 开机横幅 |
| **每 1 秒**一行 | `A 090 090 090 090` | 心跳，四路当前角度 |
| 每收到一条命令 | `S2=090 A045` / `ERR` | 动作回复 |

**这套设计的用意：把「收不到」和「发不出」分开定位。**

```text
能看到横幅和心跳吗？
├─ 看不到  → 问题在 TX 侧：
│             串口号选错 / 波特率不是 115200 / 线没接 / TX-RX 接反 /
│             板载串口根本没桥接到 44/46 / 新固件没烧进去
│             先用  python3 tools/servo_send.py -m  监听模式确认
│
└─ 看得到，但发指令没回复 → 问题在 RX 侧：
              46 脚没接 / 接反 / 没共地 / 电脑的 TX 没接到 46
```

心跳想关掉（专心看回复时），把 `src/top.v` 里 `servo_cmd` 例化的
`HB_MS` 设成 `0`；改横幅延时用 `BOOT_DELAY_MS`。

### 2.5 角度标定：直接发角度（`SCALE_360 = 0`）

**舵机是 180 度的，所以协议里的值直接就是角度**：发 `2090` = 2 号舵机转到 90 度。

（早先误以为范围是 0-360，所以做过一层"0..360 映射到 0..180"的 ×2 换算。
现在 `SCALE_360 = 0`，那层映射关掉了，省得来回换算搞混。
需要时改这个参数就能切回去，见下表。）

| `SCALE_360` | 含义 | 例子 |
|---:|---|---|
| **0（当前）** | 收到的值直接就是舵机角度 0..180，1 度/单位 | 发 `2090` → 2 号转到 **90 度**<br>发 `2180` → 2 号转到 **180 度**<br>超过 180 判非法 |
| 1 | 收到的 0..360 映射到舵机 0..180，0.5 度/单位 | 发 `2180` → 2 号转到 **90 度**<br>发 `2360` → 2 号转到 **180 度** |

改的话**两边都要改**：`src/top.v` 里 `servo_cmd` 例化的 `SCALE_360`，
和上位机的 `--scale360`。窗口标题栏会显示 GUI 当前用的是哪个。

### 2.6 上位机怎么用

**⚠️ 这台机器上有两个 python，别用错：**

| 命令 | 版本 | tkinter | pyserial |
|---|---|---|---|
| `python3`（miniforge3，默认） | 3.13 | 有 | **没有** |
| **`/usr/bin/python3`**（系统自带） | 3.9 | 有 | **有** ✅ |

**直接用 `/usr/bin/python3`，不用装任何东西。**

#### GUI 版（推荐微调时用）

```bash
/usr/bin/python3 ../tools/servo_gui.py
```

界面上有 4 个滑块，每个对应一路舵机，**拖到哪舵机就转到哪**（0–180 度）：

- 滑块显示的是**舵机实际角度**，标签里同时显示对应的协议原始值
- 拖动时界面上每秒最多发 16 条指令（自动节流，见脚本头部注释 ①）
- 上方实时显示 FPGA 每秒回读的四路角度 —— 可以对照滑块看舵机有没有到位
- 「全部回中位 90°」一键归中
- 日志区显示回执 / 错误 / 开机横幅；心跳不刷日志（否则一秒一行刷屏）

```bash
# 指定串口
/usr/bin/python3 ../tools/servo_gui.py -p /dev/cu.usbserial-1120

# FPGA 里 SCALE_360 改成 0 了，这边要跟着改，否则差一倍
/usr/bin/python3 ../tools/servo_gui.py --scale360 0
```

> ⚠️ `--scale360` 必须和 `src/top.v` 里 `servo_cmd` 例化的 `SCALE_360` 一致。
> 不一致的话滑块拖到 90 度舵机会跑到 45 度（或反过来 180）。
> 标题栏里会显示当前的 `SCALE_360`。

#### 录制 / 回放（GUI 里）

面板上多了一栏「录制 / 回放」：

| 按钮 | 作用 |
|---|---|
| **● 开始录制** | 把每一次**真正发到 FPGA 的指令**连时间戳记下来（挂在发送节流里，记的就是串口上真实发生的事）|
| **保存… / 打开…** | 存成 JSON，能存档、能发给别人复现问题 |
| **▶ 回放** | 按原时间戳重发，支持 **0.25x / 0.5x / 1x / 2x / 4x** 变速和**循环** |
| **清空** | 丢掉当前记录 |

回放时 4 个滑块会跟着动，但会被**禁用**（防止手动操作和回放互相干扰），
进度显示在右侧 `12/30  t=4.2s`。

**这个功能对排查很有用**：先录下"出问题的那一段操作"，之后就能**确定性复现**，
而不用靠手抖去重现。

#### 时间轴编辑：让四个舵机**同时**动

**为什么需要**：录制的时候你一次只能拖一个滑块，所以时间戳天然是错开的 ——
回放出来永远是"你一下我一下"。要让四路同时动，必须能**事后改时间轴**。

面板上多了一栏「动作编辑（时间轴）」，**4 行 = 4 路，横轴是时间**：

```text
  舵机1  ●                    ← 蓝色圆点 = 一条动作
  舵机2     ●                 ← 红色 = 已选中
  舵机3        ●
  舵机4           ●
         0s    0.5s   1.0s
```

| 鼠标操作 | 作用 |
|---|---|
| 单击圆点 | 选中 |
| **Shift + 单击** | **加选** |
| 空白处单击 | 取消选中 |
| 按住拖动 | 改时间（按「吸附」栅格对齐）|
| 滚轮 | 缩放 |
| 双击圆点 | 改这一条的角度 |

| 按钮 | 作用 |
|---|---|
| **对齐选中** | **把选中的几条落到同一时刻 —— 这就是"同时动"** |
| 吸附全部 | 所有时间量化到栅格（如 100ms），把"差一点点"的自动并成一组 |
| 整条通道平移 | 某一路整体提前/推后 N 毫秒 |
| 合并重叠 | 同一路连续重复的相同角度只留第一条（清理拖动产生的冗余）|
| 删除选中 / 撤销 / 全选 | 常规编辑，**每步都可撤销**（保留 80 步）|

**最常用的三步**：

1. 四路各自"到位"的那一条 **Shift 多选**起来
2. 点 **「对齐选中」** → 它们落到同一时刻
3. 点 **「▶ 回放」** → **四个舵机同时动**

实测（对齐前后回放同一段记录）：

```text
对齐前  1090 在 +0.000s   2045 在 +0.150s   3030 在 +0.300s   4150 在 +0.450s
对齐后  1090 2045 3030 4150   全部在 +0.000s        <- 同时
```

#### 起始位：让回放**可复现**

**为什么必须有**：录制只能从"当时那个姿势"开始。如果回放时不先回位，
夹子可能正夹着东西、手臂可能停在半路 —— **第一段动作就完全走样了，
每次回放结果都不一样**。

所以：

- **开始录制时会自动记下当时的四路位置**作为起始位
- **回放时先发这四条指令**把机械臂送回同一姿势，**等设定时间**（默认 600ms）
  让舵机真的到位，**然后才开始走时间轴**

实测一次完整回放：

```text
   +   0 ms   回位      1020  2160  3075  4040     <- 四条同时发
   + 302 ms   时间轴    1100                       <- 等了 300ms 才走
   + 603 ms   时间轴    4010
```

面板上还有：

| 控件 | 作用 |
|---|---|
| **以当前位置为起始** | 手动重新采一个起始位（不重新录制也能改）|
| **回到起始位** | 只回位，不回放（比如手动操作前先把手臂摆正）|
| **回放前先回位** | 勾选框，默认开。关掉就按当前姿势直接放 |
| **600 ms 等待** | 回位后等多久才开始走时间轴，按你的舵机速度调 |

起始位会**一起存进 JSON**，所以存档发给别人也能完整复现。

> 回放开始时会**对记录做一次快照**，所以回放当中你去编辑时间轴也不会把
> 正在播的东西改乱 —— 编辑只影响下一次回放。

> 如果记录里没有起始位，回放时会**报警告**：结果会依赖当前姿势。

> 载入记录时会检查里面的 `scale360` 和当前设置是否一致，不一致会警告 ——
> 否则回放出来的角度会差一倍。

#### 命令行版

脚本在 [`../tools/servo_send.py`](../tools/servo_send.py)：

# ★ 第一步永远先跑这个：监听模式，只看 FPGA 发什么，不发送
/usr/bin/python3 ../tools/servo_send.py -m
#   看到开机横幅 + 每秒一行心跳 → TX 链路通了，再看 RX
#   什么都没有                      → 问题在 TX 侧，见第 7 节

# 交互模式
/usr/bin/python3 ../tools/servo_send.py

# 或者直接发一条
/usr/bin/python3 ../tools/servo_send.py 2090
/usr/bin/python3 ../tools/servo_send.py 1090 2180 3270 4360
```

脚本会**自动跳过心跳行**去等真正的回复 —— 否则每秒一行的心跳会把回复冲掉。
判断规则：只有 `S<1-4>=ddd Addd` 和 `ERR` 才算回复，横幅里的
`Send 4 digits...` 虽然也以 S 开头，但不会被误判。

macOS 上找不到串口时，先看一眼设备名：

```bash
ls /dev/tty.usb* /dev/tty.wchusbserial* /dev/tty.SLAB*
```

也可以用任何串口终端（minicom / screen / Gowin 自带的串口工具），
**115200 8N1，关闭流控**，直接敲 4 个数字。这时你会看到心跳每秒刷一行，
那是正常的。

### 2.7 舵机脉宽标定

本工程默认按 **500–2500µs = 0–180°** 标定（MG996R 等常见规格）。
另有一大类舵机是 **1000–2000µs = 0–180°**（很多 SG90）。

判断方法：**先只烧一路、只接一个舵机试**。症状对照：

| 现象 | 说明 |
|---|---|
| 舵机只转一半行程就到头、伴随嗡嗡声 | 脉宽范围给大了，把 `PULSE_MAX_US` 从 2500 降到 2000 |
| 舵机在两端"顶住"异响 | 同上，或机械限位已到 |
| 舵机抖动 / 不受控 | 供电不足（回到 2.1），或信号线太长、没共地 |

脉宽参数在 `src/top.v` 的 `servo_pwm` 例化里：`PULSE_MIN_US` / `PULSE_MAX_US`。

### 2.8 自动扫描模式（备用）

`src/top.v` 里把 `SERVO_CTRL_MODE` 从 `0` 改成 `1`，就切回"4 路 ±45 度
自动往复"的接线排查模式：

```verilog
localparam SERVO_CTRL_MODE = 0;   // 0 = 串口手动微调   1 = 自动扫描
```

扫描模式下 4 路 **相位差 22 度**，任意时刻位置都不同。

> ⚠️ 为什么必须错开相位：如果 4 路参数完全一样，Gowin 会判定它们
> "逻辑等价"并**合并成一路**再扇出到 4 个脚（实测综合日志报
> `g_servo[1..3] is swept`）。功能上没错，但 4 个脚输出完全相同的波形，
> 你就无法判断"3 号舵机到底接在 41 还是 42 上"。
> 串口模式（模式 0）各路角度本来就互不相同，不受影响。


## 3. 写代码时的 5 条硬规矩

违反任何一条，后期移植都会痛。这些规矩来自 138K 主工程已经踩过的坑
（见 `../../fpga_project/MOTOR_DRIVER.md`）。

**① 绝不写死时钟频率**

每个模块第一个参数一律 `parameter CLK_FREQ`，顶层必须显式传
`localparam CLK_FREQ = 27_000_000`，不许依赖默认值。

```verilog
arm_joint_pid #(
    .CLK_FREQ (CLK_FREQ),   // ← 必须传，别用默认值
    .CTRL_MS  (1)
) u_pid0 ( ... );
```

**② 绝不例化器件原语**

可移植模块里不许出现 `rPLL` / `PLL` / `DPB` / `SDPB` / `OSC` / ROM IP。
需要时钟就套 wrapper（`clk_gen.v` 就是这么做的）。
需要存储就用数组让工具推断，不要直接例化 BSRAM 原语。

**③ 需要"慢时钟"就用使能脉冲（tick），不要分频出新时钟**

```verilog
// 好：单时钟域，用 tick 控制节奏
localparam TICK_MAX = CLK_FREQ / 1000;      // 1kHz
always @(posedge sys_clk) if (tick) begin ... end

// 坏：分频出新时钟去驱动逻辑，会引入新时钟域，移植时全是 CDC 问题
```

**④ 调参集中到一个头文件**

`KP` / `KI` / 控制周期 / 关节限位 / 减速比 / 编码器线数，全部放
`src/arm_cfg.vh` 里，各模块 `\`include` 它。不要散在各模块的 localparam ——
138K 主工程现在就散在 `top.v` 里，移植时必然冲突。

**⑤ 单位钉死，写进注释**

"关节角是 0.01 度还是 raw count"、"PID 周期是 1ms 还是 10ms"必须写死。
138K 主工程在这上面出过真实事故：`MOTOR_DRIVER.md` 主张"计数/闸门"，
而 `fs/README.md` 描述的是"计数/秒"，**差 100 倍**，闭环直接不成立。

## 4. 移植到 138K 时怎么做

**可移植的模块**（直接复制）：`servo_pwm.v` / `servo_sweep.v` / `servo_cmd.v` /
`uart_rx.v` / `uart_tx.v`，以及以后写的 `arm_*.v`。对每一个执行：

```
1. 复制  4k/fpga_project/src/servo_pwm.v  →  fpga_project/src/servo_pwm.v
   （以此类推；同一文件在两边各存一份，改动要同步，别只改一边）
2. 编辑  fpga_project/fpga_project.gprj 的 <FileList> 加一行
3. 编辑  fpga_project/src/top.v，照 4K 侧 top.v 的舵机段例化，
         并把 CLK_FREQ 从 27_000_000 改成 50_000_000
4. 管脚重映射：4K 引脚 43/42/41/40 → BX72 的 Gpio0 / Gpio1
         对照 fpga_project/PINOUT.md 逐脚确认（★ 这一步最容易出错）
5. 重跑综合 + P&R，**必看时序报告**
```

**不要搬的 4 个文件**：`clk_gen.v` / `bx4k.cst` / `bx4k.sdc` /
`pnr_dual_purpose.tcl`。138K 那边各有对应版本。

**移植后第一件要确认的事**：这些模块都是参数化的，只要 `CLK_FREQ` 传对，
在 50MHz 下输出的脉宽、周期、波特率与 27MHz 时**逐拍一致**（500–2500µs /
20ms / 115200 都不变）。如果上板发现舵机往一边偏、或者串口乱码，
第一个要查的就是 `CLK_FREQ` 是不是忘了改。

### ✅ 已经实测过移植了 —— 结果是安全的

不是推测，是**真的在 138K 上编译了一遍**：把本目录的 RTL 原样拿过去，
只改 `CLK_FREQ` 一处（27→50MHz），器件选 `GW5AT-LV138PG484AC1/I0`，
约束 50MHz，跑完整流程：

| | GW1NSR-4C（4K，27MHz） | GW5AT-138（138K，50MHz） |
|---|---:|---:|
| 实测 Fmax | **82.4 MHz** | **146.2 MHz** |
| 余量 | 3.05× | **2.92×** |
| 时序违规 | 0 | 0 |
| Logic | 1072 / 4608（24%） | 1083 / 138240（**<1%**） |
| DSP | 4.25 / 8（54%） | 5 / 298（**2%**） |

**138K 比 4K 快约 2.9 倍**，同样的逻辑过去余量反而更大。
唯一值得留意的是 4K 上 DSP 用了 54%（每路舵机 1 个乘法器），到 138K 只占 2%。

### ⚠️ 但"4K 上能跑"不等于"138K 上一定能跑"—— 还是每次都要看报告

138K 主工程的记录（`MOTOR_DRIVER.md`）：机械臂/电机里的乘除法一旦写得随意，
`clk50` 的 Fmax 会从 **87.586 MHz 掉到 29.275 MHz**，44 个端点 setup 失败。

**本项目已经踩过两次同样的坑**（详见 6.2 节）：
- `servo_pwm.v` 第一版组合乘法器 → Fmax **41.9 MHz**
- `servo_cmd.v` 第一版 `ang100*100` / `ang10*10` → Fmax **36.5 MHz**

两次都在 27MHz 的 4K 上"侥幸能过"，搬到 50MHz 的 138K 就会挂。
**所以：改完任何带乘除法的逻辑，都要重跑 P&R 看 Fmax，不能只看"编译过了"。**

### 6.5 移植到 138K —— 真机编译验证过，不是推测

把本目录的 RTL 原样拿过去，**只改 `CLK_FREQ` 一处**（27→50MHz），
器件选 `GW5AT-LV138PG484AC1/I0`，约束 50MHz，跑完整流程：

| | GW1NSR-4C（4K，27MHz） | GW5AT-138（138K，50MHz） |
|---|---:|---:|
| 实测 Fmax | 57.6 MHz | **166.0 MHz** |
| 余量 | 2.13× | **3.32×** |
| 时序违规 | 0 | 0 |
| Logic | 735 / 4608（16%） | 734 / 138240（**<1%**） |
| DSP | 4.25 / 8（54%） | 5 / 298（**2%**） |
| Register | 532 / 3573（15%） | 538 / 139095（<1%） |

**138K 比 4K 快约 2.9 倍，同样的逻辑过去余量反而更大。**

> 4K 上 DSP 用了 54%（每路舵机 1 个乘法器），到 138K 只占 2%。
> 但如果以后在 4K 上加到 8 路以上舵机就会超。真要扩展，把角度→脉宽的乘法
> 改成多路分时复用（角度是秒级更新的，完全来得及），或者改成累加式
> （角度每变 1°，脉宽加一个固定量，连乘法都不需要）。

### 6.6 时序踩坑记录（两次，都差点埋雷）

| 模块 | 第一版写法 | Fmax | 修法 |
|---|---|---:|---|
| `servo_pwm.v` | 乘法+加法+比较全组合 | 41.9 MHz | 拆 3 级流水 → **101.3 MHz** |
| `servo_cmd.v` | `ang100*100` / `ang10*10` 用真乘法器 | 36.5 MHz | 百位改比较器、乘 10 改移位相加 → **57.6 MHz** |
| `servo_cmd.v` | 加开机横幅 + 心跳 + 4 路十进制转换（逻辑翻倍） | — | 路径反而更短 → **82.4 MHz** |

两次都在 27MHz 的 4K 上"侥幸能过"，搬到 50MHz 的 138K 就会挂。
期间还试过把 `/10` 换成魔数乘法 `(v*205)>>11`，结果 15 位移位加法树
**反而更慢**（43.3 MHz），已放弃 —— 这些都记在 `servo_cmd.v` 的注释里了。

### 6.7 预期内的警告（不是错误，不用管）

1. `WARN (NL0002) The module "clk_gen" / "servo_sweep" ... is swept in optimizing`
   —— 直通时钟零逻辑、模式 0 下用不到扫描模块，被优化掉了。正常。

2. `WARN (PR1014) Generic routing resource will be used to clock signal 'Clk_d'`
   —— 引脚 45 在器件里是 `LPLL_T_in`（专用 PLL 输入脚），不经过 PLL 时
   时钟走的是通用布线资源。**实测两种方案下都出现**，当前 0 违规、
   Fmax 远超 27MHz，无实际影响。规模变大后若出现 hold 问题，优先查这条，
   那时切到 `clk_gen.v` 里的 `pll_27`。

## 7. 上板自检与排查

### 7.1 顺序（**先别接舵机**，每一步都能单独定位问题）

1. Gowin IDE 打开 `fpga_project.gprj`，确认器件是 **GW1NSR-4C / GW1NSR-LV4CQN48PC6/I5**
2. **确认源文件列表里有 `servo_cmd.v` / `uart_rx.v` / `uart_tx.v`**
   （IDE 缓存着旧的列表，改过 `.gprj` 后要关掉工程重新打开）
3. Synthesize → P&R（确认 `src/pnr_dual_purpose.tcl` 已运行）
   → 时序报告 `clk27` 违规为 0
4. 烧 **SRAM**，**LED 每秒闪一次** → 器件、27MHz 时钟、工具链全部正确
   （若约 0.54 秒一次 → 某处误用了 `50_000_000`）
5. **先不接舵机，跑监听模式**：
   ```bash
   /usr/bin/python3 ../tools/servo_send.py -m
   ```
   应该看到开机横幅 + 每秒一行心跳。**这一步是分水岭**，见 7.2。
6. 发送 `1090`，应回 `S1=090 A045`；发 `5090` 应回 `ERR`
7. **不接舵机，用示波器/万用表量引脚 43/42/41/40**：
   发 `1090` 时 43 脚应出现 50Hz 方波、高电平约 1.0ms；
   发 `1270` 时应变成约 1.5ms。其余三路不动。
8. 接**一路**舵机（信号线 + 独立 5V 电源 + 共地），发指令确认动作正常、范围对
9. 依次接上其余三路
10. 全部正常后开始微调

### 7.2 「输入了没反应」怎么查

**第一件事：确认你烧进去的是新版固件。** 如果综合时源文件列表里没有
`servo_cmd.v`，那个比特流里根本没有串口，怎么发都不会有反应。

然后跑监听模式 `python3 ../tools/servo_send.py -m`，按结果分岔：

| 现象 | 结论 | 下一步 |
|---|---|---|
| **看不到横幅、也没有心跳** | 问题在 **TX 侧** | 见 7.3 |
| 有横幅和心跳，但发指令没回复 | 问题在 **RX 侧** | 见 7.4 |
| 有回复，但内容是乱的（乱码） | 波特率或时钟不对 | 见 7.5 |
| 有回复但舵机不动 | 舵机侧问题 | 见 7.6 |

### 7.3 看不到横幅和心跳（TX 侧）

按可能性从高到低查：

1. **固件没烧进去 / 烧的是旧版** —— 板上 LED 有没有在闪？
   LED 每秒闪一次说明固件在跑；LED 不闪就是根本没配置成功。
2. **串口号选错** —— `ls /dev/tty.usb* /dev/tty.wchusbserial* /dev/tty.SLAB*`
   看看有几个口，逐个试。Gowin 的 Programmer 能连上，不代表那个口就是 UART。
3. **板载 USB 串口根本没桥接到 44/46** —— 这正是 2.2 节说的那个资料矛盾。
   **最省事的验证：拿外接 USB-TTL 模块**，TX 接 44、GND 接 GND，
   在电脑上监听。能看到横幅就说明 FPGA 在发，是板载桥接的问题。
4. **波特率不是 115200** —— 终端设成 115200 8N1 无流控。
5. **44 脚虚焊或没引出来** —— 换个脚试（改 `bx4k.cst` + 重编）。

> 提示：监听模式下**先按一下板上复位键**，横幅会重发一次，不用等。

### 7.4 有横幅但发指令没回复（RX 侧）

1. **46 脚没接 / 接反** —— 电脑的 TX 必须接到 FPGA 的 46。
   用外接 USB-TTL 时最容易搞错：模块的 TXD → FPGA 46，RXD → FPGA 44。
2. **没共地** —— 电脑地和 FPGA 地必须连通。
3. **46 脚内部上拉已经开了**（`PULL_MODE=UP`），悬空时应该读高电平；
   如果量出来一直是低，说明短路或接错。
4. **发送时带了额外字符** —— 其实没关系，非数字字符只会清空计数。
   但如果你用脚本连着发，前一条的尾巴可能被当成新帧的开头，
   中间停 100ms 以上最稳。
5. 用示波器量 46 脚：发一条指令时应该能看到一串脉冲。
   没有脉冲 → 电脑根本没发出来（串口选错/被别的程序占着）。

### 7.5 回复是乱码

说明 TX 通了但流控/速率不对，按顺序查：

1. 终端波特率是不是 115200
2. 数据位 8 / 停止位 1 / 无校验 / **无流控**
3. `top.v` 里的 `localparam CLK_FREQ` 是不是 `27_000_000`（写错会整体变速）
4. `servo_cmd` 例化的 `BAUD` 和终端是否一致

### 7.6 串口正常但舵机不动

- **某一路不动、其余正常** → 那一路的线或舵机问题
- **四路都不动** → 量 43/42/41/40 有没有波形。有波形就是供电或舵机问题
- **舵机通电就抖 / FPGA 反复重启** → 供电问题，回 2.1 节，别从板子取电
- **舵机只转一半行程就到头** → 脉宽标定不对，见 2.7 节

### 7.7 【真实踩坑记录】烧录后舵机自己来回摆

**现象**：烧录完成后，4 个舵机不听指挥，自己平滑地来回摆动，
约 2 秒一个完整来回，而且 4 路**错开**、不同步。串口也完全没反应。

**诊断**：这个运动的参数正好是「模式 1 自动扫描」的签名 ——

| 看到的 | 对应参数 |
|---|---|
| 来回摆 | `SERVO_HALF = 45` → 45°↔135° |
| **约 2 秒一个来回** | `SERVO_SWEEP_MS = 1000` × 2（双程）= 2000ms |
| **4 路错开** | `SERVO_PHASE_STEP = 22` → 相位 0/22/44/66 度 |

而扫描版**根本没有串口模块** —— 这正好解释了"串口也没反应"。

**根因**：板上跑的不是刚烧的固件，而是 **Flash 里的旧固件**。

> ⚠️ **Gowin Programmer 默认只烧 SRAM，掉电就没了。**
> 配置 Flash 里的内容不会因为烧一次 SRAM 而改变。
> 所以：烧 SRAM → 立刻能用；一旦断电/复位 → 回到 Flash 里的旧程序。

**怎么确认是这个问题**（不用接示波器）：

```bash
/usr/bin/python3 ../tools/servo_send.py -m
```

| 结果 | 结论 |
|---|---|
| 看到开机横幅 + 每秒心跳 | 新固件在跑，问题在电气侧（看 7.3 / 7.6）|
| **什么都没有，舵机却在摆** | **板上是旧固件** ← 就是这个坑 |

**修法：把 Flash 也烧一遍**

```text
Gowin Programmer
  -> 选中器件
  -> Edit -> Configure Device
  -> Access Mode 从 SRAM 改成 Flash
     （GW1NSR-4C 没有片内用户 Flash，所以是 External Flash）
  -> 重新 Program
  -> 断电重上电，再跑一次监听模式确认
```

**事后改进（已做）**：

- `src/top.v` 顶部加了醒目警告，说明这个运动形态意味着什么
- 本节的诊断表

**教训**：每次改完代码，**SRAM 和 Flash 都要烧**，或者至少记得
"烧完 SRAM 只验证了这一次上电，掉电后跑的还是老的"。
调试阶段用 SRAM 快速迭代没问题，但**一旦要长期跑，必须烧 Flash**。

### 7.8 【真实踩坑记录】拖任何滑块都只有一路舵机动

**现象**：GUI 上 4 个滑块，不管拖哪一个，**效果都一样**；
而且滑块的某一段范围完全无反应。

**根因**：`servo_cmd.v` 里接收组帧和数字锁存**跨了两个 always 块**。

```verilog
// 组帧块：收到第 4 位时做移位
if (nd == 3'd3) begin
    d0 <= d1; d1 <= d2; d2 <= d3; d3 <= rx_data[3:0];   // ← 这里把 d1/d2/d3 覆盖了
    fire <= 1'b1;
end

// 另一个 always 块：下一拍才去锁存
if (fire) begin
    cid <= d1;    // ← 读到的已经是"第 2 位"，不是舵机号！
    cr1 <= d2;    //    第 3 位
    cr2 <= d3;    //    第 4 位
    cr3 <= rx_data;  //  第 4 位（重复）
end
```

于是**舵机号变成了角度值的百位数字**：

| 滑块位置（SCALE_360=1 时） | 发出的值 | 被当成舵机号 | 结果 |
|---|---|---|---|
| 0-49 度 | 000-098 | 0（非法）| **完全无反应** |
| 50-99 度 | 100-198 | 1 | 舵机 1 |
| 100-149 度 | 200-298 | 2 | 舵机 2 |
| 150-180 度 | 300-360 | 3 | 舵机 3 |

拖哪个滑块都一样，因为百位只跟角度大小有关，跟你想控制哪一路无关。

**修法**：把锁存和移位放进**同一个 always 块**，用移位**前**的旧值锁存。

**为什么之前的验证没抓到这个**（这条比 bug 本身更值得记）：

我给协议解析写过一个 Python 模型，当时是这么建的：

```python
if nd==3:
    cid,cr1,cr2,cr3 = d[1],d[2],d[3],n     # 假设"锁存"和"移位"同一拍完成
    d=[d[1],d[2],d[3],n]
```

**模型把 RTL 的两个 always 块合并成了一步**，正好绕过了这个 bug。
模型和 RTL 结构不一致时，模型通过 ≠ RTL 正确。

后来把模型改成**严格逐周期**（每个字符一拍，第 4 位之后**再多跑一拍**
让"下一级"看到 valid 信号），才复现出现象。

**教训**：

1. **跨 always 块的"前一拍数据"不能想当然**。非阻塞赋值的移位和
   另一个块的读取之间差一拍，这一拍足以让数据全错。
2. **验证模型必须和 RTL 的结构（always 块的划分）对应**，
   不能只对应"算法意图"。结构不一致的模型会给你虚假的安全感。
3. 组合逻辑的 bug 靠"读代码"和"综合通过"都发现不了 ——
   要么逐周期仿真，要么严格逐周期建模。
